### Motion

The card changes by handing values over, not by replacing them: the outgoing value and the
incoming one are on screen together, and the direction of travel says which way the script
moved. Forward, the old value goes up and out while the new one rises into its place;
backward, the reverse. Everything shares one duration and one curve —
**450ms, `cubic-bezier(.42, 0, 0, 1.01)`** — with a 70ms hand-off lag so the new value
starts a beat after the old one leaves.

| What | How it changes |
|---|---|
| Section name | Rolls, with its width animated so the counter beside it doesn't jump |
| Counter `(X/Y)` | X rolls; Y is set, because it only ever changes when the name does |
| Body number `1.2` | Same split — the part rolls, the section digit is set |
| Body (question + marks) | One unit, cross-fading with no travel |
| Card height | 450ms on `--ease-drawer`, so it lands with the content |
| Recording dot | 1.7s pulse to 17px at 70% alpha, with the two outer rings breathing |

`rollTo(slot, fill, dir)` in `windows.html` does the work: it drops anything still leaving
(a held arrow key outruns the animation and the ghosts would stack), moves the outgoing
copy to `position: absolute` so the slot takes the incoming value's size — which is what
lets the card's height animate to where it is actually going — commits the start state with
a forced reflow, then releases it. Direction is derived in `setDocSection` by comparing the
new absolute part index against the old, so clicking a passage in the document moves the
mini bar the same way stepping does.

`prefers-reduced-motion` keeps the cross-fade, which is what explains the change, and drops
the travel and the hand-off lag.

Three things the height animation cost, all of them non-obvious:

- **`interpolate-size: allow-keywords` does nothing here.** It makes `auto` interpolable,
  but the card goes `auto → auto` — the *used* value changes, the computed one doesn't, so
  no transition ever fires. The height has to be written out in pixels.
- **The height belongs on `.toolbar-surface`, not the card.** `.toolbar-surface` is
  `height: 100%`; against a card at `height: auto` that is circular, and Chrome resolves it
  to a few pixels on the first pass. Symptom: the card comes up ~11px tall with the bar
  overflowing it.
- **Measure with `offsetHeight`, never `getBoundingClientRect()`.** The browser window
  scales open from the taskbar icon, and a rect is reported through every ancestor
  transform — mid-animation the whole card measures under 15px. Measure the *panel*
  (`.compact-bar` / `.compact-complete`) too, not the surface: the panel keeps its natural
  height while the surface is animating through a value that is nobody's answer.

A `ResizeObserver` on the panel is what keeps it honest afterwards. `document.fonts.ready`
is not enough — it resolves before the last face lands, and the intro paragraph rewraps by
four lines after it.

Also fixed while here: `.compact-bar` was `aria-hidden` while the expand button inside it
still held focus. `setPanelHidden()` sets `inert` first — which moves focus out — and
aria-hidden second.

### Tuning it — `?dials=1`

Every duration, delay and travel distance above is a custom property on `:root`; nothing is
written inline in a rule. `--rae-speed` scales the whole set at once. **`?dials=1`** loads
`motion-dials.js`, which mounts **DialKit** (joshpuckett/dialkit) over the call. It reads
its starting values out of the stylesheet — the panel never invents a default — and writes
back to the same properties. The Roll group's Value control is a DialKit *easing* control,
carrying the 450ms and the bezier together with a live curve preview; Card Height is
another. The rest are number dials, plus Replay / Back / Copy CSS actions. Values and named
versions persist under `rae-dials`.

Vue, motion and DialKit load as ES modules from esm.sh, so there is still no bundler and no
`package.json`; the shipped page fetches none of it. **The dials need network access** — if
the CDN is unreachable the panel logs a warning and the prototype runs unchanged.

Four things that setup depends on, each of which fails quietly rather than loudly:

1. **Direct CDN URLs, not an importmap.** esm.sh resolves DialKit's own `vue`/`motion`
   imports to the same URLs, so there is one Vue instance and reactivity works. An
   importmap with `?external=vue,motion` 500s.
2. **`productionEnabled: true`.** esm.sh serves production builds and DialKit renders
   `null` in production by default — without it the panel mounts, resolves values, writes
   every property correctly, and shows nothing at all.
3. **Numeric dials are tuples**, `[value, min, max, step]`. An object resolves to
   `undefined`.
4. **`useDialKit` returns a `ComputedRef`**, so the values are behind `.value`.

**A dial only affects the next transition**, so the panel replays once a value settles
(260ms after the last change) — the card steps, which is the only thing that shows both the
values handing over and the height travelling. Replay ping-pongs at the ends of the script,
so repeated tweaking bounces between two questions instead of running out.

Two more things the panel keeps straight: an overridden duration is written back as
`calc(420ms * var(--rae-speed))` rather than a flat `420ms`, or the Speed dial silently
stops working; and a persisted session overrides the stylesheet, so after changing a
default in the file, clear `rae-dials` (or use DialKit's Reset) before trusting what you see.

## 12. Scrolling between sections — Paper `24M-0`

**The document is a real scroller.** The first attempt at this animated between two
sections and locked the wheel to one section per gesture. It read as neither smooth nor
snapping: short scrolls did nothing at all and a long throw still only moved one section.
Replaced by the browser's own scrolling, which is what was wanted all along — it follows
the wheel the whole way, carries through several sections on a long throw, and settles.

Every section is `min-height: 100%` with `scroll-snap-align: start`, in a `.doc-scroll`
that is `scroll-snap-type: y mandatory`. `.doc-page` carries `height: 100%` purely so that
`100%` on a section resolves to a screenful; the sections then overflow it, and that
overflow *is* the scroll. Six sections, each exactly the port height, tops at exact
multiples of it. The whitespace under a short section is what the frame shows, and now it
is a real screenful rather than a display swap.

**Landing is finished by hand.** CSS snapping does it for most gestures but not for all of
them — a scroll that ends by running out of momentum gets left tens of pixels short, and a
section resting half off the top is the one thing this layout must never do. 90ms after the
last scroll event, whichever section is nearest gets scrolled to properly. It settles: the
corrective scroll fires events of its own, the check runs again, and the second pass is
already within a pixel.

**Which section you are on is read back, not remembered.** The wheel moves the document
without asking anyone, so `docSection` follows the scroll position rather than driving it,
and the mini bar follows from there. `setDocSection` takes a third argument for the one
case that must not scroll — the read-back itself, or it and the scroller would chase each
other. Arrow keys, the link and a passage click all scroll; from the mini bar, where there
is no document laid out to scroll, the sidebar catches up on `rae:shape` instead.

**One way on, in the corner of the panel.** It reads *Scroll to next section* now, so it no
longer names where it points and no longer has to travel with a section: one small button,
`absolute` in the bottom right of `.script-doc`, outside the scroller, staying put while the
sections go past underneath. It hides on the last section — nowhere to point.

(It began as one link per section, in flow under each one, naming the section it pointed at.
That was right while the text was specific; a generic label makes the per-section copies pure
duplication.) `.has-questions` still moved from the document to the section — the rhythm
belongs to the section being read.

### Questions are numbered, restarting at 1 in every section

The number sits *inside* the question, right where the frame keeps its (empty) "Question
Number Text" slot, not out in the gutter beside the circle: the circle is the thing you tick,
the number is part of what you read. A 27px slot, the frame's, in a flex row — so the text
lines up down the section and a question that wraps hangs under its own first word rather
than under the number.

A CSS counter can't do it: the sections that aren't on screen are `display: none`, and a box
that is never generated never increments anything. So the numbers are written in once at
start-up, resetting at each `<ol>`. The drawn one is `aria-hidden` — the `<li>` already
carries its position, and it would otherwise be read twice.

(This ran 1..15 across the whole script for a while, on the reading that question 5 is the
fifth thing you ask, with a matching `start` attribute to keep the reading order honest.
Per-section is what was wanted, and it needs neither.)

The numbers go in *after* the `script` model is read off the document, so the mini bar's copy
stays "Could you tell me a bit about yourself?" rather than "1. Could you tell me…" — it
already carries its own `1.2`.

### Taken differently from the frame
- **The gutter stays at 29px.** The frame sets a question row's bullet gap to 10px (text at
  47) while its own section heading sits at 53 — so question text would start 6px left of
  its own heading, and jump sideways every time you moved from a prose section to a
  numbered one. Kept 16px / 53 everywhere, which is what §10 and §11 already settled.
- Its heading reads "Section 1 - Warm up" and its link "Section 2 - Background". Ours are
  read off the real script, as they have been since §10.

## 13. What Rae heard — Figma `374:25895`, `374:26045`, `374:26204`, `374:26277`

Section 1 is a conversation you advance by clicking. Each click is another stretch of
listening; Rae writes up what she has, and the next click gets what she has after that.
Four frames, four moves:

    1  answer 1 streams, ticks -> answer 3 streams (no tick) -> answer 4 streams, ticks
    2  Q2 answers and ticks, carrying two things she would follow up on
    3  both follow-ups land, so Q2's line is rewritten and the chips fold into it
    4  Q3 stops being inferred — rewritten, and now it ticks

**A key that comes back has been revised, not added to.** `SCRIPTED_MOVES` is a list of
lists; a step names a beat, the line she now has for it, and whether the question closes
there. When a step lands on a beat that already has a line, the old one fades out over
200ms before the new one starts arriving — otherwise the new words come up on top of the
ones they replace. A question already ticked stays ticked: the tick is a fact about the
question, not about the latest thing written under it.

**`MARKS` is the mini bar's model and stays that way.** Deriving it from the moves — letting
later ones overwrite earlier ones to land on where each part ends up — reads as tidier than
it is: it silently changed what the bar says, dropping Q2's two probe chips for Q2's finished
answer. The bar shows one part at a time and always has; the sidebar walks the conversation a
move at a time. Two models on purpose. Reverted.

**The line and its probes are two things on one row.** Two flex items, side by side while
they fit and the chips dropping to their own row when they don't — `column-gap: 8px`,
`row-gap: 4px`. The first attempt did it with inline margins, which put the wrapped chips
8px right of where they belong, because a margin at the start of a line is still a margin.
A row of chips is one item now, so a wrap takes all of them together.

The row carries the hanging indent so a wrapped chip lands under the *text*; the line itself
is pulled back out by the same amount and hangs its own wrapped lines back in — a whole
answer, indented from within. The indent is `1.283em`, the measured width of "— " at 12px,
not the frame's 13px: that was drawn against a different rendering of the dash, and 2px out
is visible when a chip is meant to sit under the first word. Measured after: the chips start
0.01px from where the text starts, 4px under it.

**A rewrite is quieter than a first draft.** Moves 3 and 4 correct a line rather than break
news, so they arrive faster (44ms a word rather than 64), with no overshoot, and mostly as a
fade — 3px of travel over 240ms against the first draft's 6px, 1.6px of bounce and 360ms.
The correction shouldn't ask for the attention the original did.

**A probe is written as a question.** The chips end in a question mark, added where they are
drawn rather than in the data: every probe is one she would ask, in both surfaces, and none

## 14. Section 2, and a note too long for its gap

Figma `374:26712` (the questions), `375:26901` (a note folded), `376:26980` (opened),
`374:26307` (the checked mark).

**Section 2 is now "Background", with six questions** — its four Kingston ones plus two
about the session itself. Long enough that the section no longer fits: 916px against an
836px panel, which is what the rest of this entry is about.

**Inside a section the wheel is just the wheel.** No CSS snapping anywhere in this document,
and no animation inside a section either — the delta is applied straight to `scrollTop`,
clamped to the section, so a casual scroll moves with your fingers and comes to rest at the
end of the section rather than running on into the next.

> A section that doesn't fit is scrolled. At either end of a section, a gesture is worth one
> section, and that move is a snap.

Standing at the top of section 2: swipe up and it snaps back to section 1; swipe down and it
scrolls, as far as you push it, stopping at the end of section 2; swipe down again and it
snaps to section 3.

**A snap is `cubic-bezier(0.76, 0.01, 0.06, 1)` over 500ms** — slow off the mark, a hard run
through the middle, a long settle. 500ms is the time to cross the panel's own height, which
is what a section to the next section is; a shorter snap takes proportionally less, so they
go at the same speed rather than for the same length of time.

There is no way to hand the browser a `scrollTop` to animate, so the curve is solved in JS
the way the browser solves one: Newton-Raphson for the `t` at a given `x`, bisection where
the curve is too flat for it, then read `y` off that. Checked against the browser's own
`cubic-bezier(0.76, 0.01, 0.06, 1)` by pausing a Web Animation at eleven points along it —
they agree to four decimal places, worst case 0.0001.

Three things it has to get right, each of which was wrong at some point:

**Arriving at the end is not the same as asking to leave it.** The gesture that ran you into
the end of a section stops there; the next one moves on. A gesture is judged by where it
began, which is what a plain lock cannot express.

**A gesture that has snapped is spent.** Its tail must not then scroll the section it has
just arrived in — which only section 2 has the room to do, and which read as the document
bouncing after it had landed. Arriving at section 2 from either side, the tail now moves
nothing: measured, the scroll never passes 1072 coming down or drops below 1456 coming up.

**A gesture ends when the hand does, not when the events do.** A gap in the events was the
only test at first, which fails twice over: at 160ms a mouse wheel's own notches fell inside
one gesture, so scrolling twice in a row got you one section; and a trackpad keeps sending
for over a second after the fingers lift, so a second swipe landing on that tail was read as
part of it and thrown away — the delay you had to wait out.

The gap is 90ms now, and the shape of the deltas is the second test. A swipe ramps up, peaks,
then decays; only the decay is inertia. So the gesture's own peak is tracked: once the deltas
have fallen below a quarter of it the tail has set in, and a delta climbing back above half
the peak after that is a hand rather than a tail. Comparing against the peak rather than
against the last delta is what keeps a swipe's own ramp-up from reading as half a dozen new
gestures — measured with a realistic stream (ramp 3, 9, 24, 52, 80, then 28 decaying events),
one swipe moves exactly one section, and two swipes with no gap at all between them move two.

**A snap owns the scroller for the rest of its own gesture.** The handler used to cancel any
landing in progress on every wheel event, so the tail of the gesture that asked for the snap
killed it a frame later — the document twitched and stayed put. A *new* gesture still takes
over at once, and the move it interrupts finishes there and then rather than being abandoned
part way: read the section off a scroller mid-flight and you get one it was only passing
through.

And one detail: coming up into a section, you arrive at its bottom — the end you are about to
read up through — but only if it is genuinely scrollable. A section that overflows by less
than its own trailing air has no bottom to arrive at, and landing there just pushed its
heading off the top by the 8 or 13 pixels it overflowed by.

Walked with simulated swipes — ramp, peak and decaying tail, the shape a trackpad sends.
Down: 532, 1072, 1456 (section 2's end, scrolled to), 1988, 2097 (section 3's end), 2629,
3174. Up: exactly the same seven in reverse. Back-to-back swipes with no gap between them
move once each, in both directions.

**The way on waits.** *Scroll to next section* is hidden while there is more of the current
section below the fold — offering to skip past what you have not read is worse than not
offering at all. It appears when the section's bottom reaches the panel's.

**A note is written into a two-line window.** Not clipped at two lines — *written into* them:
once the writing passes the second line the older lines slide up out of the window and you
watch the newest one arrive, the way text does while something is still writing it. Before
that it was writing on down the page out of sight, and after the first two lines you saw
nothing more happen.

All the words are in the DOM from the first frame — only their opacity is staggered — so the
window cannot follow the height, which never changes. It follows the word that is *arriving*,
worked out from the clock and the same per-word gap the animation delays were built from,
and eases toward it rather than jumping, or a line's worth of travel every few frames reads
as a flicker.

Two things it has to measure carefully, both of which shivered before they were fixed. It
follows where the word is **laid out**, not where it is drawn: every word is mid-animation as
it arrives — rising 6px, overshooting 1.6 — so a target read off `getBoundingClientRect`
wanders by that much every tick and the window shakes chasing it. `offsetTop` does not move.
And the easing runs on a number of our own rather than reading `scrollTop` back each tick:
the browser rounds what it returns, and a lerp fed its own rounding jitters on the spot
instead of settling. Measured across a whole note: 0, 9, 16, 17.5, 18, 28.5, 35, 36, 48, 53
— not one backward step while the writing runs. The fade and the chevron appear at the moment the writing passes the second
line, not before: until then there is nothing more to show.

When the writing stops the window eases back to the top, which is the note's beginning and
what the folded state is there to show — the frame has it folded from the first word.
Measured through one: `scrollTop` 0 while the first two lines are written, the chevron
arriving at ~520ms, then 1, 3, 10, 20, 39, 50 as the note runs on, then 20, 2, 0 as it
settles. The window stays 36px throughout and the questions below it never move.

Folded, the second line fades out rather than being cut off — the sentence carries on, it
just isn't on screen. The fade ends exactly where the chevron begins and the chevron carries
the same white behind it: a first pass left a 6px strip between the two with half-clipped

Folded, the note lives in the 69px under the question and moves nothing. **Opened it needs

## 17. Clicking the card did nothing under a real pointer

The follow-ups in §16 tested clean and did not work when Mohammad tried them. Neither did
stepping — the mini bar had not advanced on a click since the drag was written.

`makeDraggable` took `setPointerCapture` on `#compact-bar` at **pointerdown**, before
knowing whether this was a drag or a click. With a capture in force the browser retargets
the whole gesture to the capturing element, so `click` was dispatched on `#compact-bar`
itself. The listener is on `.compact-body` *inside* it, and a click on an ancestor never
reaches a descendant — so nothing on the card ever heard it.

The capture is only worth having once the gesture **is** a drag, so it is taken at the 4px
threshold instead, and `pointermove`/`pointerup` are bound to `window` — without a capture,
a pointer that leaves the card would otherwise stop reporting and the drag would stick.

**Why the tests missed it.** Every check drove the card with `element.click()`, which
dispatches a bare `click` with no pointer sequence at all — the one path the capture cannot
affect. The behaviour was verified against a mechanism the user never uses. Anything that
answers to a pointer has to be checked with a pointer: `computer` clicks at coordinates,
not `.click()`.

(Also fixed here: the mini bar's footer slab carried `aria-hidden` while holding the
focusable Start Recording button.)

## 19. A black ring around a tick you just clicked

## 27. Command works wherever Ctrl does

The prototype is going out to testers on both platforms, and every "next" in it was bound

All nine bindings in `windows.html` — the tour, the doc hint, finish session, view

const stepping = (event) => event.ctrlKey || event.metaKey;

- ~~**The static server serves stale files.**~~ FIXED. `python3 -m http.server` sends
